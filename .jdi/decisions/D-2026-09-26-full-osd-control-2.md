D-2026-09-26-full-osd-control-2 (2026-09-26): Sondagem read-only de códigos fora do caps ganha um NOVO método no port driving `MonitorControl` — `probe_undeclared_features(&self, id: &MonitorId) -> Result<Vec<ProbedFeature>, DdcError>`, com `ProbedFeature { code: VcpCode, outcome: Result<FeatureReading, DdcError> }` (novo tipo em `ddc_core::domain`). Precisa ser um método do PORT (não uma função livre na CLI) porque `ddc-cli::run` é genérico sobre `impl MonitorControl` (D-cli PLAN A-7) — sem entrar no trait, a CLI não teria como chamá-lo através da mesma abstração testável com o fake.

**Implementação** (`SoftwareOsd`, `app/software_osd.rs`): resolve capabilities (via `capabilities_or_empty`, mesmo caminho de `get_feature` — só `MonitorNotFound` propaga `Err`); itera `mccs_catalog::catalog_codes()` filtrando os já `capabilities.declares(code)`; para cada código restante, chama o MESMO caminho interno de leitura que `get_feature` usa (fatorar o corpo de `get_feature` numa função privada `read_and_track(id, code)` compartilhada pelas duas, para que um código sondado também atualize `known_max` — assim um `set` subsequente no mesmo processo sobre um código só sondado, nunca lido antes, já tem `max` disponível quando `feature.kind == Continuous`); o `Result` de cada leitura vira o `outcome` do `ProbedFeature` correspondente — uma falha individual NUNCA aborta a sondagem inteira nem o `Result` externo, só populada como `Err` naquele item. `probe_undeclared_features` NUNCA chama `write_vcp` — usa só o mesmo `backend.read_vcp` que `get_feature` já usa.

**Sem cache em disco.** Rationale: o custo de sondar os ~8 códigos fora do caps (0x1E, 0x20, 0x30, 0x62, 0x6C, 0x6E, 0x70, 0x7E, 0xC9 — 0x52 já é declarado no caps, então não conta) é dominado por leituras individuais de 44–94ms (D-2026-09-25-ddc-backends-7) mais o custo de qualquer falha — pior caso ainda menor que o custo de `read_capabilities` sem cache (2.58s) que É cacheado em disco por D-2026-09-25-cli-1. Cachear resultado de sondagem arriscaria mascarar um código que passa a responder depois de uma atualização de firmware do monitor, por uma economia que já é pequena perto do enumerate (1.1s) pago em toda invocação curta da CLI. Nenhuma persistência nova em `ddc-adapters` é necessária para esta decisão.

**Superfície:** exposta pela CLI como `ddc-cli features --probe` (D-2026-09-26-full-osd-control-3) — sem a flag, `features` só lê os códigos do catálogo já declarados no caps (zero I/O extra além do que `caps`/`get` já fazem).

Alternativa rejeitada: reaproveitar `CachingMonitorBackend<B>` (D-2026-09-25-cli-1) para persistir resultados de sondagem — descartada porque esse decorator só intercepta `read_capabilities`; estendê-lo pra também cachear `read_vcp` por código misturaria duas políticas de cache com tempos de vida diferentes (caps é estável até o usuário trocar o monitor de porta; um código "não responde" pode deixar de ser verdade) na mesma classe, violando SRP.

**Emenda 2026-09-26 (carry-over W-4 de `.jdi/phases/cli/REVIEW.md`):** D-2026-09-26-cli-4 (já committed) corrigiu o adapter `DdcHiMonitorBackend` para mapear a resposta DDC/CI "unsupported VCP code" (result code `0x01`) direto para `DdcError::UnsupportedFeature`, SEM retry — antes disso, toda falha de leitura (incluindo essa resposta definitiva do monitor) virava `Transport` só depois de 3 tentativas inúteis, e a sondagem desta phase não conseguiria distinguir "código não existe pra este monitor" de "falha de barramento". Com a correção, `probe_undeclared_features` (e quem consome seu resultado) distingue dois estados bem diferentes em `ProbedFeature.outcome`:
- `Err(DdcError::UnsupportedFeature(_))` — o monitor respondeu explicitamente que o código não existe para ele (leitura rápida, sem retry).
- `Err(DdcError::Transport(_) | DdcError::Timeout)` — o barramento falhou ou não respondeu a tempo (falha transiente, esgotou as tentativas).

Nenhum dos dois aborta a sondagem dos demais códigos (regra original inalterada). **Correção de expectativa sobre 0x7E:** o registro de hardware do orquestrador mostra 0x7E respondendo "Maximum retries exceeded" no ddcutil — ou seja, o caminho esperado para ele é `Transport`/`Timeout` (falha de barramento), NÃO `UnsupportedFeature`; esta decisão não assume que um código sondado sem sucesso vira necessariamente "não suportado" — `ProbedFeature` carrega o `DdcError` real e é a apresentação (D-2026-09-26-full-osd-control-3) que escolhe o texto certo para cada variante.
