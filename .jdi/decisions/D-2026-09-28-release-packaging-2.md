D-2026-09-28-release-packaging-2 (2026-09-28): Extensão retrocompatível de `lancar.yml` no `github-workflows` — anexar pacotes à release.

Hoje `lancar.yml` cria a tag e a release com `gh release create "$TAG" --target "$SHA" --title "$VERSAO" --notes-file "$NOTAS"` e não anexa nenhum arquivo. Esta phase adiciona:

- **Novo input `artefatos`** (string, `required: false`, `default: ""`): um único padrão glob de NOME de artefato do run (ex.: `"pacotes-*"`), passado para `actions/download-artifact` no campo `pattern:`. Vazio (o default) preserva o comportamento atual byte a byte — nenhum download, nenhum upload — retrocompatível com quem já chama `lancar.yml` sem o campo nenhuma extensão até este PR (o `ddc-control` ainda não chamava `lancar.yml`, então não há risco de quebra em consumidor existente; a extensão é validada do mesmo jeito que `so`/`pacotes_sistema`/`auditoria` em `qualidade.yml`, D-2026-09-27-ci-crossbuild-2).
- **Validação em `Conferir as entradas`** (passo já existente no job `lancar`): quando `artefatos` não é vazio, casa contra `^[A-Za-z0-9_.*-]+$` (sem `/`, sem espaço, sem metacaractere de shell) — rejeita com `::error::` antes de qualquer chamada de rede, mesmo padrão de `pacotes_sistema` em `qualidade.yml`. O valor só entra em `with:` de uma action (`download-artifact`), nunca interpolado dentro de um `run:`, mas a validação existe do mesmo jeito: um padrão broken (ex. `../../etc`, `$(id)`, glob com `;`) deve ser barrado antes de chegar à action, não confiar só na tolerância dela.
- **Novo passo `Baixar pacotes`** (`if: inputs.artefatos != ''`), depois de `Criar a tag e a release`: `actions/download-artifact@<sha do lock>` com `pattern: ${{ inputs.artefatos }}`, `merge-multiple: true`, `path: ./pacotes-baixados`. Sem `run-id` explícito: dentro do mesmo `workflow_call`, `download-artifact` já resolve o run atual.
- **Novo passo `Anexar pacotes à release`** (mesmo `if`): `gh release upload "$TAG" ./pacotes-baixados/* --clobber`, com `GH_TOKEN`/`GH_REPO` no `env` como os passos vizinhos.
- **`harden-runner` do job `lancar`:** a lista `destinos-liberados` ganha `*.actions.githubusercontent.com:443` (download de artefato) além de `github.com:443`/`api.github.com:443` já existentes — sem isso o passo `Baixar pacotes` falha por egress bloqueado (o `download-artifact` fala com o serviço de resultados de Actions, não com a API REST). Só adicionado quando `artefatos` é usado; nenhum outro passo do job muda.

`permissions: contents: write` do job `lancar` já basta para `gh release upload` (mesmo escopo de `gh release create`); nenhuma permissão nova é necessária.

**Emenda do orquestrador (2026-09-28, antes do plano). Quatro inputs opcionais a mais, todos com default que preserva o comportamento atual:**
- **`rascunho`** (boolean, default `false`): com `true`, a release sai em RASCUNHO (`gh release create --draft`). Um rascunho não cria a tag git até ser publicado, e é assim que a D-8 prova o `lancar` de ponta a ponta sem tocar a tag real. Com `rascunho: true`, a checagem "A tag ainda nao existe?" continua valendo, e nenhuma tag é criada (conferido pela API).
- **Rascunho velho da mesma tag:** antes de criar a release, o passo apaga um RASCUNHO que já exista com a MESMA `tag_name` (`gh api repos/$R/releases`, filtrando por `draft == true`, `tag_name == $TAG` e só pelo id). É o que sobra de um ensaio (D-8) ou de um run cancelado. Release publicada nunca é apagada: se já existir uma publicada com a tag, o job reprova como hoje. Sem isso, o primeiro push real na `main` esbarraria no rascunho do ensaio.
- **`changelog`** (string, default `""`): caminho de um CHANGELOG no formato Keep a Changelog. Quando dado, as notas da release começam pela seção `## [<versao>]`, se existir, senão pela seção `## [Unreleased]`, e seguem com as notas dos commits que o `versao.py` já gera. A seção é extraída por `awk` no próprio passo (não é script novo em `bin/`, D-2026-09-27-ci-crossbuild-2) e entra por ARQUIVO (`--notes-file`), nunca por linha de comando. O caminho é validado (`^[A-Za-z0-9_./-]+$`, sem `..`).
- **`SHA256SUMS`:** com `artefatos` dado, o job gera `SHA256SUMS` (formato `sha256sum`) de todos os arquivos baixados e o anexa junto com eles.
- **Egresso:** a lista `destinos-liberados` do job `lancar` sai de um run MEDIDO (harden-runner em `audit` no ensaio, lendo o relatório), com cada host justificado em comentário. Candidatos: `uploads.github.com:443` para os assets, e os hosts do serviço de artefatos (`results-receiver.actions.githubusercontent.com:443`, `*.blob.core.windows.net:443` ou o que a medição mostrar). O `*.actions.githubusercontent.com:443` acima é palpite, não fato. Depois da medição, o job volta para `block`.
