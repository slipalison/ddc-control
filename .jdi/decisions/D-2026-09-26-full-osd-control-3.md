D-2026-09-26-full-osd-control-3 (2026-09-26): Extensão da superfície `ddc-cli` (D-2026-09-25-cli-1..5, D-2026-09-26-cli-1..4) para o catálogo completo (D-2026-09-26-full-osd-control-1/2), sem introduzir nenhum subcomando novo para leitura/dump — só `features` (novo), `get`/`set` (estendidos).

**`ddc-cli features [--probe] [--json]`:** lista, por padrão, todo código do catálogo DECLARADO no caps do monitor resolvido, com `code, name (ou null), kind, access, risk, declared_in_capabilities: true, current (raw), value_name (Option, via `mccs_catalog::value_name` quando NC), interpreted (Option<String>, via `hertz`/`version_from_u16` quando aplicável)`. Com `--probe`, roda `MonitorControl::probe_undeclared_features` (D-2) e ACRESCENTA uma linha por código do catálogo ausente do caps, com `declared_in_capabilities: false`.

Um `ProbedFeature` cujo `outcome` é `Err` aparece com `current: null` e um marcador que distingue as duas causas de D-2026-09-26-full-osd-control-2 (refinado pela emenda de D-2026-09-26-cli-4): `DdcError::UnsupportedFeature` -> texto `"not supported by this monitor"` / JSON `"probe_status": "unsupported"`; `DdcError::Transport`/`DdcError::Timeout` -> texto `"not responding"` / JSON `"probe_status": "unresponsive"` — é o caminho esperado para 0x7E no monitor de dev, que falha por retries esgotados ("Maximum retries exceeded" no ddcutil), não por resposta explícita de "não suportado". Um `outcome` `Ok` ganha `"probe_status": "ok"` para os três estados serem sempre discrimináveis no JSON sem inferir a partir de campos ausentes. Nunca falha o comando inteiro por causa de um único código sem resposta. Texto: tabela; `--json`: array dos mesmos campos. Reusa a resolução de `--monitor` e o `Confirm`/exit-code table existentes — `features` nunca escreve, então nunca usa `--yes`.

**`get <name|code>`:** sem mudança de contrato, só de apresentação — quando o código tem `value_name`/`interpreted` no catálogo, a saída de texto os inclui ao lado do raw (`0x01 sRGB`, `144.00 Hz`); `--json` ganha os campos opcionais `value_name`/`interpreted` (ausentes/`null` para código fora do catálogo — nenhuma quebra de compatibilidade com o formato da phase `cli`).

**`set <name|code> <value|value-name>`:** o parser de `<VALUE>` (hoje só numérico, D-2026-09-25-cli-5) ganha um segundo caminho: se o argumento não é um número válido E a feature resolvida (via `capabilities.feature(code)`) é `NonContinuous`, tenta casar o argumento (case-insensitive) contra `mccs_catalog::value_name(code, byte)` percorrendo os bytes presentes em `feature.allowed_values` QUANDO o caps declara uma lista para o código — a lista REAL que o monitor declarou; quando `allowed_values` é `None` (código ausente do caps ou caps ilegível), percorre em vez disso os bytes de `mccs_catalog::catalog_entry(code).values` (mesmo fallback que `Feature::validate_write` agora aplica, D-2026-09-26-full-osd-control-1, emenda W-5) — a CLI não reimplementa a lógica de validação, só espelha a MESMA fonte de bytes que o core vai aceitar, para resolver um nome sem adivinhar. Um nome que existe no catálogo mas não está na lista efetiva (caps ou catálogo, conforme o caso) segue o caminho de erro já existente `DdcError::ValueNotAllowed` (exit 4, D-2026-09-25-cli-5) — sem novo tipo de erro, sem nova classificação de risco (a CLI continua nunca duplicando `Risk::`, D-2026-09-25-cli-3). Um nome que não existe em lugar nenhum é erro de uso do `clap` (exit 2), igual a um número malformado hoje.

Rationale da interseção catálogo ∩ (caps ou catálogo): o catálogo é conhecimento teórico do MCCS 2.2 para ESTE conjunto de códigos observados (D-1); `allowed_values` é o que o monitor realmente aceita quando declarado. Resolver um nome direto contra o catálogo sem checar a lista efetiva deixaria a CLI aceitar (e enviar ao hardware) um valor que nem o monitor nem o core vão validar da mesma forma — quebra a garantia "nunca escreve às cegas" de D-2026-09-25-core-domain-4 e criaria uma segunda fonte de verdade divergente da de `validate_write`.

Sem novo módulo de output: reaproveita `output.rs`/`args.rs`/`run.rs` da phase `cli` (planner tem liberdade de onde adicionar as funções, DRY com o que já existe — nenhuma tabela é duplicada).
