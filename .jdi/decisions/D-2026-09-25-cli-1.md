D-2026-09-25-cli-1 (2026-09-25): Cache persistente de `read_capabilities` por `MonitorId`, implementado como um decorator `CachingMonitorBackend<B: MonitorBackend>` em `crates/ddc-adapters` (novo módulo `caching.rs`), e NÃO como um novo port em `ddc_core::ports`. `CachingMonitorBackend` implementa `MonitorBackend` na íntegra: `enumerate`, `read_vcp` e `write_vcp` sempre delegam para `B` sem cache algum; só `read_capabilities` é interceptado — um hit no arquivo em disco retorna a string sem tocar `B` (elimina os ~2.58s medidos em D-2026-09-25-ddc-backends-7 em toda invocação de CLI depois da primeira); um miss chama `B::read_capabilities`, e só um `Ok` é persistido — um `Err` nunca é gravado nem lido do cache, a mesma filosofia que `SoftwareOsd::fetch_capabilities` já aplica no core (falha não é memória, D-2026-09-25-core-domain-4). O construtor recebe um `cache_dir: PathBuf` explícito, o que torna o decorator inteiramente testável com um diretório temporário, sem mockar `HOME`/XDG; a resolução do diretório real (`XDG_CACHE_HOME` ou `~/.cache/ddc-control/caps` no Linux, `%LOCALAPPDATA%\ddc-control\caps` no Windows) fica numa função livre `default_cache_dir()` no mesmo módulo, usada só pela composition root de `ddc-cli` — o decorator em si não conhece a política de localização, só recebe um `PathBuf` pronto. Cada monitor vira um arquivo (nome = `MonitorId` sanitizado + `.caps`), conteúdo = a string crua de capabilities tal como o backend devolve, sem serde (D-2 continua intacto: uma única string não precisa de formato estruturado). Um método inerente `invalidate(&self, id: &MonitorId)` — fora do port, só a composition root da CLI o chama, porque ela segura o valor concreto antes de movê-lo para dentro do `SoftwareOsd` — apaga o arquivo antes do próximo `read_capabilities` cair para `B`; é o mecanismo por trás de `ddc-cli caps --refresh` (única forma de forçar releitura; sem TTL, cache permanente até invalidado — como o `ddcutil`). `enumerate()` continua sem qualquer cache: já é rápido (~1.13s medido) e cachear a lista arriscaria esconder um monitor novo ou mostrar um desconectado (hotplug).

Rationale: a alternativa cogitada — um novo port `CapabilitiesStore` em `ddc_core::ports` com um adapter de arquivo — foi descartada porque exigiria alterar `SoftwareOsd` (já fixado nas phases `core-domain`/`ddc-backends`) para receber uma segunda dependência só para resolver uma latência específica de um driving adapter de vida curta (a CLI). Um decorator sobre o port já existente (`MonitorBackend`) resolve o mesmo problema sem tocar core nem o adapter `ddc-hi`, mantém D-1/D-2 intactos, e é genérico sobre `B` — o módulo não importa `DdcHiMonitorBackend` nem `ddc_hi` (gate 5.4), compõe na composition root do `ddc-cli` e é 100% testável com `InMemoryMonitorBackend`.
