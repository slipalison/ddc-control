D-2026-09-25-ddc-backends-1 (2026-09-25): Em `crates/ddc-adapters/Cargo.toml`, a dependência `ddc-hi = "0.4.1"` é declarada `optional = true`, com `default-features = false` e `features = ["ddc-i2c", "ddc-winapi"]` (exclui `nvapi` e `ddc-macos` dos defaults do `ddc-hi`). O crate `ddc-adapters` expõe uma feature própria `ddc-hi = ["dep:ddc-hi"]`, incluída em `default = ["ddc-hi"]` (default-on). `DdcHiMonitorBackend` e todo o módulo que o contém ficam atrás de `#[cfg(feature = "ddc-hi")]`; dentro dele, diferenças Windows/Linux usam `#[cfg(target_os = ...)]` (nunca no core — D-1/D-2 continuam intactos). Rationale: o feature `nvapi` do `ddc-hi` guarda `Rc<PhysicalGpu>` dentro de `Display`, o que torna `Display` (e logo `Handle`) **não-`Send`** no Windows — isso inviabilizaria a phase `tray-app`, que vai chamar o port de dentro de `tauri::async_runtime::spawn_blocking` (exige `Send + Sync`). Cortar `nvapi`/`ddc-macos` dos defaults remove essa armadilha na origem, sem perder Windows (`ddc-winapi`) nem Linux (`ddc-i2c`). Feature default-on porque este box de dev (Fedora, `systemd-devel`/libudev instalado) e a phase futura `ci-crossbuild` (windows-latest/ubuntu-latest) compilam o backend real sem flag extra — mantém os testes unitários de lógica pura (mapeamento de erro, id, VCP, retry) sempre compilados, sem matriz de features para este projeto de stack único.
