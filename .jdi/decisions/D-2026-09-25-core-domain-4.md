D-2026-09-25-core-domain-4 (2026-09-25): `MonitorControl::get_feature` executa a leitura real via `MonitorBackend::read_vcp` independente do código estar presente no `Capabilities` parseado — o core NUNCA filtra uma leitura por ausência no caps (fato observado em 2026-09-25: 0x62 volume responde no monitor "RTK QHD HDR" embora ausente da capabilities string lida). O resultado de `get_feature` carrega um campo `declared_in_capabilities: bool` (derivado de `Capabilities::vcp.contains_key(code)`) para quem consome (CLI/tray, phases futuras) decidir se avisa o usuário — o core só informa, não decide UX. `set_feature` continua exigindo um `max` conhecido para validar `value <= max`: se o código está no caps (Continuous sem lista) ou já foi lido antes (`VcpValue.max` de uma leitura prévia no mesmo processo), o max vem de lá; se não há max conhecido (nunca lido, ausente do caps, sem `allowed_values`), a escrita retorna `DdcError::UnsupportedFeature` — nunca escreve às cegas. Rationale: o fato do research (0x62 responde fora do caps) invalidaria uma regra "caps é a única fonte de verdade" se fixada cedo demais; a phase `full-osd-control` vai formalizar sondagem read-only de códigos fora do caps, então o core já precisa aceitar leitura sem caps hoje para não quebrar a API pública na phase 4.
