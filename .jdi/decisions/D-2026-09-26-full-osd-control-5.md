D-2026-09-26-full-osd-control-5 (2026-09-26): Features de tipo `Table` (LUTs multi-byte, ex.: tabela de gamma) ficam EXPLICITAMENTE fora de escopo de escrita nesta phase e em qualquer phase futura enquanto o port não mudar — `MonitorBackend::write_vcp(id, code, value: u16)` não consegue representar um payload de tabela multi-byte (é uma limitação estrutural da assinatura do port, não uma escolha de política). Nenhum código do catálogo desta phase (D-2026-09-26-full-osd-control-1) é `Table` — o "RTK QHD HDR" não declara nem responde a nenhum; a decisão é uma trava preventiva para quando um catálogo futuro (outro monitor) incluir um.

`Feature::validate_write` (`crates/ddc-core/src/domain/feature.rs`) ganha uma checagem no TOPO da função, antes de olhar `access`/`allowed_values`/`known_max`: `if self.kind == FeatureKind::Table { return Err(DdcError::UnsupportedFeature(code)); }`. `features`/`get` continuam listando um código `Table` normalmente (leitura funciona — `get_feature` nunca discrimina por `kind`, só por `access` via a UI, e o port já devolve `VcpValue{current,max}` mesmo para esses códigos hoje); só `set`/`reset` ficam bloqueados, com o mesmo `DdcError::UnsupportedFeature` (exit 4) que os códigos `Access::ReadOnly` também usam.

Rationale: expandir `write_vcp` pra aceitar um payload de tabela (`Vec<u8>` em vez de `u16`) mudaria a assinatura do port pra um caso que zero monitor observado até agora precisa — YAGNI. Travar agora com um `Result::Err` explícito (em vez de deixar o comportamento indefinido quando o primeiro código `Table` aparecer num catálogo futuro) é a opção fail-safe barata: um `unwrap`/pânico ou um valor truncado silenciosamente enviado ao hardware seriam as alternativas ruins.

**Correção 2026-09-26 (pós-review da phase `cli`, `.jdi/phases/cli/REVIEW.md` § W-5):** a frase original desta decisão descrevia o exit 4 como "o mesmo exit code 4 (`UnsupportedFeature`) que já existe hoje para qualquer feature sem `max` conhecido" — essa afirmação deixou de ser verdade depois de D-2026-09-26-cli-1 (max agora é APRENDIDO por uma leitura quando desconhecido, não recusado de cara) e da restrição desta mesma phase a `Continuous` (D-2026-09-26-full-osd-control-1, emenda W-5, que introduz um fallback de lista do catálogo para `NonContinuous` sem lista do caps). O texto acima já foi corrigido para não depender dessa premissa: a checagem de `kind == Table` continua incondicional e roda ANTES de qualquer lógica de max/lista — o mecanismo em si nunca dependeu de "não haver max conhecido", só do `kind`, então nenhuma mudança de comportamento é necessária aqui, só a correção da frase. **Ordem de execução:** em `SoftwareOsd::set_feature`, esta checagem (`kind == Table`) roda no MESMO ponto e pela MESMA razão que a nova checagem de `Access::ReadOnly` da emenda W-5 de D-2026-09-26-full-osd-control-1 — antes de `max_for_write`, para que um código `Table` (hipotético, nenhum observado ainda) também nunca custe uma leitura de backend desperdiçada.
