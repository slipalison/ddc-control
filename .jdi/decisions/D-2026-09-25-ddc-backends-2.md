D-2026-09-25-ddc-backends-2 (2026-09-25): `MonitorId` é derivado dentro de `ddc-adapters` (nunca no core) a partir do que cada caminho do `ddc-hi` realmente oferece — os dois esquemas coexistem no mesmo adapter, escolhidos em tempo de execução pelo que `DisplayInfo` trouxer, não por `#[cfg(target_os)]`: (a) EDID disponível (`manufacturer_id` + `model_name`/`model_id` + `serial`/`serial_number` — caminho típico do backend `ddc-i2c` no Linux): chave = `"{manufacturer_id}-{model-normalizado}-{serial}"`, sanitizada (não alfanumérico vira `-`). Quando o serial é um valor-placeholder conhecido por colidir entre unidades idênticas (ex.: EDID serial string vazia + serial binário `0x01010101`, observado no "RTK QHD HDR" de dev) e duas entradas do mesmo `enumerate()` produzem a mesma chave, a segunda em diante recebe sufixo `#2`, `#3`... na ordem de enumeração — documentado como limitação conhecida (não sobrevive a hotplug reordenando a lista), nunca como falha silenciosa. (b) EDID ausente (caminho do backend `ddc-winapi` no Windows, que só popula `description` via `DisplayInfo::new(backend, description)`): chave = descrição normalizada (sanitizada como acima) quando não-vazia; se também vier vazia, cai para `"index-{N}"` (N = posição no `Vec` retornado por `Display::enumerate()`) — único caso em que um índice puro de enumeração é aceito como id, e só porque não existe qualquer outro dado de identidade disponível nessa plataforma. Rationale: a regra geral do projeto ("nunca identificar só por índice de enumeração — desloca no hotplug", specialist doer) continua valendo como default; este é o fallback documentado para quando o próprio `ddc-hi`/Windows não expõe EDID.
